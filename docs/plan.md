# 구현 가능성과 초기 설계

작성: 2026-10-15 / 기획 v0.2.0. 출처에 있는 기능과 우리 환경에서 검증한 결과를 구분한다. 아직 스트리밍 실험은 하지 않았다.

## 결론

브라우저에서 Windows PC를 조작하는 솔루션은 구현 가능하다. 접속 기기는 웹을 쓰되, 대상 PC에는 네이티브 캡처·입력 프로그램이 필요하다. 브라우저 화면 공유 API는 사용자의 공유 선택을 필요로 하므로 상시 무인 접속의 호스트로 삼지 않는다. [S1]

추천은 기존 영상 엔진 + 웹 클라이언트 개선이다. Sunshine과 비공식 moonlight-web-stream을 우선 검증하고, 관리·복구 용도로 MeshCentral을 비교한다. 한영 입력과 모바일 터치까지 해결되는지는 실기기로 판정한다. 게임 목표는 감독모드의 화면 확인과 연속경기 시작을 위한 수동 클릭이며 실제 경기 플레이는 제외한다.

무료 소프트웨어, 클라우드 영상 중계 0, 모든 네트워크에서 언제든 연결을 동시에 보장할 수는 없다. 전원·인터넷이 끊긴 PC에는 접속할 수 없으며, 제한된 네트워크에서는 중계가 필요할 수 있다. [S4]

## 벤치마킹

| 후보 | 역할과 장점 | 이번 목표에서 확인할 점 | 초기 판단 |
|---|---|---|---|
| Sunshine + MrCreativ3001/moonlight-web-stream | 하드웨어 인코딩 호스트 + WebRTC 브라우저 게이트웨이 | 비공식 클라이언트, 한글 조합·터치·Safari 실측 필요 | 첫 기술검증 후보 |
| MeshCentral | 브라우저 원격 화면·터미널·파일 관리 | 게임 영상 품질, 한글 입력, 실제 중계 경로 검증 | 업무 복구 비교 후보 |
| Apache Guacamole + VNC/RDP | HTML5 원격 접속 게이트웨이 | 게이트웨이를 클라우드에 놓으면 영상 트래픽 경유. RDP의 세션·잠금 동작은 현재 콘솔 사용 목표와 대조 필요 | 관리 업무 중심 대안 |
| noVNC + Windows VNC 서버 + WebSocket 연결 | 브라우저 VNC, 모바일 지원 | GPU 게임 화면·지연·서버별 한글 입력 검증 | 단순 화면 제어 비교군 |
| Sunshine + 네이티브 Moonlight | 저지연 스트리밍, 여러 OS 클라이언트 | 접속 기기에 앱 설치 필요 | 웹 품질이 부족할 때 대안 |
| Selkies | 브라우저 스트리밍 구현 참고 | 확인한 2.0 문서는 Linux 호스트만 지원 | 현재 Windows 호스트 직접 채택 제외 |

근거: [S2][S3][S5][S6][S7][S8]. Sunshine 자체의 웹 UI는 설정·페어링용이며 브라우저 스트리밍 클라이언트와 다르다. 비슷한 이름의 Moonlight Web 프로젝트가 여러 개이므로 저장소를 정확히 구분한다. 릴리스와 개발 브랜치 문서를 섞지 않는다.

## 권장 구조 — 검증 전 제안

```text
맥 / 아이패드 / 아이폰 / 안드로이드 브라우저
    ├─ HTTPS: 웹 UI, 인증, 연결 협상
    └─ WebRTC: 영상·오디오 / 입력 데이터
                  ↕ 우선 직접 연결
Windows PC 또는 같은 LAN의 웹 게이트웨이
                  ↕ 로컬 스트리밍 프로토콜
Windows PC의 Sunshine → 현재 콘솔 화면 / OS 입력

직접 연결 실패 시: TURN 중계 또는 지원되는 WSS 대체 경로
```

게이트웨이는 단순 로그인 서버가 아니라 영상 경로의 일부다. 이를 Oracle VM에 올리면 WebRTC라고 해도 PC→VM 구간의 영상이 클라우드를 통과한다. PC에 같이 두는 구성이 초기안이다. [S3]

외부에서 웹 UI까지 도달하는 방법과 WebRTC 영상이 도달하는 방법은 별도 문제다. STUN만 추가해도 집의 HTTPS 서버가 인터넷에 공개되는 것은 아니다. 도메인/인증서, 공인 주소와 공유기 설정, 또는 별도의 터널/접근망 설계가 필요하다. 특정 게이트웨이를 클라우드 시그널링 서버와 분리할 수 있는지도 구현 확인 전 가정하지 않는다.

| 연결 방식 | 영상 클라우드 경유 | 제약 |
|---|---|---|
| 같은 LAN | 없음 | 1차 검증에 적합 |
| 집 HTTPS + 도달 가능한 주소/포트 + WebRTC 직결 | 없음 | 공인 IP·방화벽·공유기·인증서 운영 필요, 모든 외부망을 보장하지 않음 |
| VPN 연결 후 웹 접속 | 직접 터널이면 없음 | 기기별 VPN 설정 필요. VPN도 구성에 따라 중계될 수 있음 |
| TURN 중계 | 클라우드 TURN이면 있음 | 연결 가능성을 높이지만 전송량·지연·운영비 증가 |
| HTTPS/WSS 영상 프록시 | 클라우드 프록시면 있음 | 443 사용만으로 무료·직결이 되지 않음 |

CGNAT나 이중 NAT가 있으면 단순 포트포워딩만으로 해결되지 않을 수 있다. 첫 외부망 실험에서 경로를 확인한다. 중계 없는 초기안은 직접 연결 불가 시 명확한 오류를 보여주고 대안 경로로 전환한다. [S3][S4]

## 트래픽 계산

영상 단방향 데이터의 십진 GB 근사치: Mbps × 0.45 × 사용 시간(h). 오디오·프로토콜·재전송 오버헤드는 별도다.

| 평균 비트레이트 | 1시간 | 하루 2시간 × 30일 |
|---|---:|---:|
| 3 Mbps | 1.35 GB | 81 GB |
| 8 Mbps | 3.60 GB | 216 GB |
| 15 Mbps | 6.75 GB | 405 GB |
| 25 Mbps | 11.25 GB | 675 GB |

직결이면 이 데이터는 집 업로드와 접속 기기 다운로드에 사용된다. 중계 시 서버는 수신·송신을 모두 처리한다. 사업자의 과금 대상 방향과 합산 방식은 별도 확인해야 하며 표의 두 배가 무조건 청구되는 것은 아니다.

Oracle Cloud 무료 제공량은 계정·상품·시점에 따라 확인할 사항으로 남긴다. 이번 설계는 특정 무료 한도에 의존하지 않는다. 예산 알림은 트래픽 차단 장치가 아니므로 중계를 도입하면 애플리케이션에서 허용량·비트레이트·세션 시간 상한을 집행해야 한다.

## 사용자 불편을 해결할 설계

### 게임 화면

화면 캡처, 인코딩, 전송, 브라우저 디코딩, 게임 입력을 분리해 원인을 찾는다. Windows Desktop Duplication은 전체 화면 DirectX 캡처를 위한 기반을 제공하지만 보호된 콘텐츠에는 제한이 있다. 피파온라인 지원을 뜻하지는 않는다. [S9]

창 모드 / 테두리 없는 창 / 전체 화면, HDR, 다중 모니터, 모니터 꺼짐을 조합해 확인한다. 먼저 1080p SDR H.264를 후보로 시험하고 실제 브라우저 협상 결과를 기록한다. 게임 보안 프로그램의 입력 차단은 우회하지 않는다.

### 한영 입력

물리 키 전달과 완성 문자열 전달을 별도 모드로 설계한다. 브라우저의 한글 composition 이벤트 처리 중 문자와 keydown이 중복 전송되지 않게 한다. 모바일은 로컬 입력창에서 조합 완료 후 전송하는 대체 경로를 둔다. 클립보드 기반 전송은 앱별 붙여넣기 제한과 내용 노출을 고려해 명시적 동작으로만 수행한다.

호스트 한영 버튼은 클라이언트 표시만 바꾸지 않고 Windows 쪽 입력 동작으로 연결한다. 상태를 확실히 읽지 못하면 '한글 상태'로 단정하지 않는다. 게임의 키 입력과 터미널의 문자 입력은 따로 검증한다. SendInput은 권한 수준에 따른 제한이 있어 관리자 앱·UAC를 별도 시험한다. [S10]

### 터치 스크롤과 단축키

두 손가락 움직임은 원격 wheel 이벤트로 변환하고, 원격 화면 영역에서는 페이지 자체 스크롤과 충돌하지 않게 한다. 감도·방향·미세 이동 누적을 조절한다. 전용 스크롤 띠와 PageUp/PageDown은 보조 수단이며 터미널 종류에 따라 동작이 다를 수 있다.

키보드가 올라올 때 화면 높이 변경, 가로/세로 회전, 확대 후 좌표 변환을 시험한다. OS와 브라우저가 가로채는 단축키는 화면 버튼을 제공한다. 연결 종료·포커스 상실 시 modifier 키가 눌린 채 남지 않게 한다.

## 무인 접속과 복구

Windows 서비스 자동 시작, 장애 후 재시작, 인증서 갱신, 호스트 오프라인 표시가 필요하다. 잠금 화면, 로그인 전, UAC 보안 데스크톱은 같은 화면으로 취급하지 않고 별도 검증한다. 브라우저 백그라운드 전환 이후에는 재연결을 예상한다.

절전·전원 종료까지 복구하려면 Wake-on-LAN 지원과 상시 동작하는 LAN 내 장치 등 별도 구성이 필요하다. OS 정지·정전까지 해결하려면 하드웨어 원격 관리/전원 장치가 필요할 수 있어 초기 범위에서는 제외한다. 모든 접속 수단을 같은 PC에 두면 PC 장애라는 공통 원인은 남는다.

외부 공개 전에는 HTTPS, 강한 인증과 다중 인증, 세션 만료/철회, 로그인 시도 제한을 갖춘다. 관리 UI와 원격 조작 권한을 구분한다. 최초 관리자 생성은 로컬에서 마친다. RDP/VNC 포트를 직접 인터넷에 공개하지 않는다. TURN을 쓴다면 인증과 만료·사용량 제한을 적용한다.

## 단계별 실행 계획

1. 환경 조사: GPU 인코더, 공유기/CGNAT, 업로드 속도, 기기·브라우저 버전, VPN 허용 여부를 확인한다.
2. LAN 기술검증: 버전을 고정한 Sunshine + moonlight-web-stream으로 현재 화면·피파온라인·한국어·터치 스크롤을 실기기 시험한다. 이 단계에서 설치와 설정을 진행한다.
3. 채택 판단: 화면은 좋고 입력만 부족하면 웹 클라이언트를 개선한다. 게임 화면이 실패하면 네이티브 Moonlight와 비교해 캡처 문제와 브라우저 문제를 구분한다. 업무 복구는 MeshCentral과 비교한다.
4. 외부망 검증: 모바일 데이터와 외부 Wi-Fi에서 웹 UI 도달성과 영상 연결을 각각 확인한다. 직결/중계 및 전송량을 기록한다.
5. 사용자 기능 개발: 한영 버튼, 문자열 전송, 터치패드/스크롤, 특수키, 연결 상태·오류 표시를 구현한다. 호스트 측 추가 기능은 재사용 엔진의 한계가 확인된 경우에만 개발한다.
6. 안정화: 재부팅·모니터 꺼짐·장시간·재접속 검증 후 버전을 태그하고 이전 버전 복구 절차를 기록한다.

검증 전 개발 기간과 완전 호환을 확약하지 않는다. 첫 성공 기준은 '휴대폰 브라우저에서 현재 PC 화면 확인 → 한글 명령 입력 → 터미널 스크롤 → 끊김 후 복귀'다.
